# Contract change proposals — WP12

Append one entry per proposed change. Changes must be additive. The orchestrator merges them into
`src/core/*` and records the decision in STATUS.md.

## 2026-09-24 — `CollisionWorld.floorAt` semantics the controller relies on (doc comment)
- **WP:** WP12
- **Change:** doc-only, `src/core/runtime.ts` `CollisionWorld.floorAt`:
  ```ts
  /** Highest walkable surface <= feetY + stepMax at (x, z): the cell floor (NOT for SOLID or VOID cells, and never a
   * cell floor above feetY + stepMax), WALKABLE_TOP box tops whose footprint contains (x, z) (+-1 mm: boxes are
   * Float32), ramp planes. -Infinity if nothing qualifies (e.g. a VOID pit with no box below); NaN if unloaded. */
  floorAt(x: number, z: number, feetY: number): number;
  ```
- **Rationale:** WP12 treats NaN as "unloaded = solid", falls when the floor is > 5 cm below the feet and uses a
  second probe `floorAt(x, z, feet + height - stepMax)` to detect stair flights beside / above the body. Pits only
  work if VOID cells contribute no floor (WP12's collision build adds a catch box at -6 m, so the fall ends there
  if no pit portal fires). Returning a cell floor above feetY + stepMax would let the player climb any step.
- **Consumers affected:** WP10 (WorldQueryImpl.floorAt). tests/player/helpers.ts `TestWorld.floorAt` is a reference
  implementation of exactly this.

## 2026-09-24 — Extra collision boxes: cell risers and soffits (doc comment)
- **WP:** WP12
- **Change:** doc-only, `src/core/mesh.ts` `ChunkCollision.boxes`: "also contains per-cell RISER boxes (a cell whose
  floor is above a neighbour's: [lowest neighbour floor, floor], WALKABLE_TOP) and SOFFIT boxes (a low ceiling next
  to a higher one: [ceil, neighbour ceil]); border cells assume an unknown neighbour (risers down to -7 m)".
  Boxes may extend below y = 0 and outside the chunk by WALL_T / 2.
- **Rationale:** floor-height steps between cells are not edges, so without boxes they would not block (a 1.2 m
  loading-dock drop could be walked up) and a 1.5 m ceiling would not stop a standing player. Validators
  (WP10 validatePayload) must not reject negative y or boxes that overhang the chunk by 7.5 cm.
- **Consumers affected:** WP10 (validatePayload, boxesNear), nobody else reads ChunkCollision.

## 2026-09-24 — `PlayerInput.up` (fly-mode ascend)
- **WP:** WP12
- **Change:** `src/core/player.ts`:
  ```ts
  export interface PlayerInput { ...; up?: boolean } // Space: ascend in fly mode (fly=1); ignored otherwise
  ```
- **Rationale:** §5 WP12 asks for "vertical movement on Space and C" in fly mode, but PlayerInput has no field for
  Space. WP12 currently uses `PlayerInputExt` (controller.ts, `extends PlayerInput { up?: boolean }`) and
  input.ts writes the extra property onto the poll target. Making it official lets WP14's input drivers set it.
- **Consumers affected:** WP12 (input.ts, controller.ts), WP14 (App input object literal, optional).

## 2026-09-24 — Input actions + live settings for `InputSource` (optional members)
- **WP:** WP12
- **Change:** `src/core/runtime.ts`:
  ```ts
  export interface InputSource {
    ...;
    /** Esc / F3 / F4 / gamepad Start: app actions (WP14 wires them to pause / overlay / debug view) */
    onAction?: ((a: 'pause' | 'overlay' | 'debugView') => void) | null;
    /** live settings (toggleSprint / toggleCrouch / sensitivity for gamepad look) */
    setSettings?(s: Settings): void;
  }
  ```
- **Rationale:** §5 WP12 lists Esc pause, F3 overlay and F4 debug view among the input keys, but InputSource can
  only report PlayerInput. input.ts already implements both members (see `InputExt`) and additionally dispatches a
  `window` CustomEvent `'backrooms:input-action'` with `detail.action`, so WP14 can use either without a cast
  once the members are in the contract. `createInput` receives a settings snapshot, so toggle-sprint/crouch changes
  made in the settings panel need `setSettings`.
- **Consumers affected:** WP14 (App.ts: subscribe settings -> input.setSettings; onAction -> pause/overlay/view).

## 2026-09-24 — `createAutopilot(seed, clock?)`
- **WP:** WP12 (own signature, optional trailing parameter)
- **Change:** `export function createAutopilot(seed: number, clock?: () => number): Autopilot;` (seconds; default
  `performance.now() / 1000`).
- **Rationale:** the autopilot needs a time step to turn and change speed smoothly; `next()` has no dt. A fake
  clock makes it deterministic in tests and under WP14's scaled-time autowalk.
- **Consumers affected:** none required (WP14 autowalk may pass its own clock).

## 2026-09-24 — Behaviour notes for WP14 (no type change)
- **WP:** WP12
- **Change:** documentation of PlayerSystem behaviour:
  - `teleport(s, ...)` with `s !== state.s` calls `host.switchStorey(s)` itself (so a teleport to another storey
    shows that storey); calling `streamer.switchStorey` again is harmless if WP10 makes it idempotent.
  - `teleport(..., y = null, ...)` snaps to `floorAt(x, z, 1.5)` once the chunk is loaded; a spawn inside geometry
    is moved to the nearest free cell centre (<= 3 cells) on the first loaded frame.
  - `update(..., frozenTime = true)`: movement still advances on real time (so QA walks work under `time=`), but
    head bob, breathing and camcorder noise are frozen (deterministic captures).
  - The object returned by `createPlayerSystem` also has a read-only `debug` view (steps, towerSwitches, towerClamp,
    glitchPush, elevatorPhase, warping, unstuckCount) for the F3 overlay / QA.
- **Consumers affected:** WP14.

## 2026-09-25 — Follow-ups (no type change)
- **WP:** WP12
- **Change:** documentation only.
  - `CollisionWorld.floorAt`: WP10's implementation returns the lowest surface ABOVE `feetY + stepMax` when
    nothing is within reach (instead of `-Infinity`). WP12 now accepts both behaviours: a floor above step reach is
    never snapped onto or landed on (controller.ts), which `tests/player/realQuery.test.ts` checks against the real
    `createWorldQuery`. The first proposal above can therefore be read as "`-Infinity` OR any value
    `> feetY + stepMax` when no walkable surface is within reach; NaN only when unloaded".
  - Live input settings: `PlayerSystem` forwards bus `settingsChanged` to `updateInputSettings()` (player/input.ts),
    which updates every `createInput` source. WP14 does not have to call `setSettings` itself; the optional
    `InputSource.setSettings` proposal above is still useful for other hosts but is no longer required.
- **Consumers affected:** none.

## 2026-09-25 — Audit follow-up (no type change)
- **WP:** WP12
- **Change:** documentation only. `teleport(..., y = null, ...)`: when `floorAt(x, z, 1.5)` finds no walkable surface
  within reach (a SOLID cell reports a surface far above; a bare VOID cell `-Infinity`), the feet are placed at the
  storey datum y = 0 and the spawn check moves the player to the nearest free cell centre (<= 3 cells). Previously
  the player was placed on the reported surface (e.g. 8.7 m up inside a SOLID mass) and then fell.
- **Consumers affected:** none (WP14 debug teleports benefit).

## 2026-09-25 — Second audit follow-up (no type change)
- **WP:** WP12
- **Change:** documentation only.
  - Glitch / pit warp hold: the trigger emits `glitch` once (glitch walls 0.8 s at strength 1, pits 1.2 s at 0.6). If the target
    storey is not prefetched yet when that glitch runs out, one hold event `{seconds: 1.0, strength}` follows, then
    another every 1.0 s until the teleport. Hold events never overlap the previous glitch and are never closer than
    WP13's tape-stop cycle (0.4 s stop + 0.6 s silence). Waits are normally zero: the storey below is now
    prefetched (radius 1 chunk, 0.25 s keep-alive) around every glitch and pit portal within 12 m, and around the
    player the moment a warp starts. Suggestion for WP13: `Dread.onGlitch` could ignore a `glitch` that arrives while
    `graph.tapeSilent` and just extend the silence, so a long hold is one continuous tape stop.
  - Elevator door leaves: besides the tracked elevator (nearest within 14 m, which runs the ride), up to 4 other
    elevators within 40 m show their two leaves parked open, with their virtual collision boxes (rescanned every 1 s
    with `portalsNear(x, z, 40)`). They are released on storey change, teleport and beyond 40 m.
  - Collision head room: a move is refused when an overhang (`ceilingAt`: a ramp soffit, a box underside or a low
    cell ceiling) is below the top of the head, including the head raised by a step up. The knee-to-head walkable
    surface test (ramps as solid wedges) and the head room are sampled at the centre and 4 rim points (0.9 r), so the
    body keeps its radius off stair flights as off boxes. A player who starts a move already violating one of these
    rules is not held by it, so they can always walk out.
  - Gamepad look speed scales with `settings.mouseSensitivity` (2.8 rad/s at the default 0.0022, clamped to
    0.25x..4x).
- **Consumers affected:** WP13 (optional tape-stop suggestion above).
